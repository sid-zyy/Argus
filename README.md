# Incident Commander AI (Argus)

Alert + logs + git history in; evidence-checked root cause, sandbox-tested fix and human-approved incident report out.
See `BUILD_PLAN.md` for the design.

## Setup
```
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
copy .env.example .env   # add GEMINI_API_KEY and/or GROQ_API_KEY
```

## Run
```
uvicorn ui.app:app --port 8000 --reload                    # dashboard at http://localhost:8000
python -m orchestrator.main scenarios/incident1_conn_leak -v   # terminal run, asks for approval
python -m orchestrator.main ... --provider ollama          # offline on the local model
python -m orchestrator.main ... --save-replay              # also write replay/<scenario>.json (enables the Replay button)
python -m orchestrator.replay replay/incident1_conn_leak.json   # terminal demo fallback, no network
python -m eval.run_eval                                    # scorecard across all scenarios (real model calls)
python -m pytest -q tests                                  # offline tests with a scripted fake model
```
Restart the server after Python changes (or use `--reload`). Pages stamp their assets with the file's modification time
and send `Cache-Control: no-cache`, so a normal reload always shows the latest UI.

## Scenarios
| Scenario | Service | Real cause | Planted trap |
|---|---|---|---|
| `incident1_conn_leak` | checkout-api | early `return` skips `pool.release()` (code) | "database overloaded" |
| `incident2_timeout` | checkout-api | `REQUEST_TIMEOUT` lowered 30 → 3 s (config) | "payment provider is slow" |
| `incident3_cache_oom` | catalog-api | unbounded page cache keyed by full URL (resource) | "marketing traffic spike" |

Each folder has `history.py` (commits), `generate_logs.py` (deterministic telemetry), `repro.py` (the sandbox check) and
`expected.json`; `repo/` and `logs/` are generated by `python -m scenarios.build <name>`.

## Users and approvals
Demo users (pick one in the top-right menu; no passwords): Tara (tester), Siddhartha and Meera (developers), Yuvika (lead).
The chosen user is kept in a signed cookie and the server checks the role on every write.
- Testers file bug reports (they start the agents like an alert) and confirm fixes in QA ("verified" closes the ticket,
  "still failing" re-runs the agents).
- Developers approve sev 3/4 fixes, assign, change severity and re-run escalated or rejected incidents.
- Sev 1/2 fixes need two different people, at least one a lead. Whoever reported the issue cannot approve its sev 1/2 fix.
- The AI never approves; a rejection needs a reason.

## UI
- Dashboard (`/`): Argus status, stat tiles, kanban board, recent activity, and a queue of what waits on the signed-in user.
- Ticket (`/incidents/{id}/view`): Argus, claims and verdicts with cited evidence, suspect diff, fix and sandbox
  before/after, approvals, QA, report, activity and comments.
- Argus (`argus.js`) is a rotating node-and-edge sphere (the orchestrator). Each agent owns a region; the working agent's
  region lights up, sparks run along its edges and pulses travel to its card. Drag to rotate, hover a region to see whose
  it is, click a region or card to see that agent's recent steps.

API: `POST /alerts`, `POST /bugs`, `GET /incidents[/{id}]`, SSE at `/incidents/{id}/events`, `POST /incidents/{id}/approve|reject|qa|rerun|comment`,
`PATCH /incidents/{id}`, `GET /metrics`, `GET /events/recent`, `GET|POST|DELETE /session`, `GET /users`, `POST /demo/trigger/{scenario}?mode=live|replay`.
Incidents are stored in `incidents.db` (SQLite; older databases are migrated on start). Each run also writes
`runs/<scenario>-INC-<id>-<time>/incident_report.md` and `trace.json`.

## Layout
- `llm.py`: Gemini / Groq / Ollama through OpenAI-compatible APIs, with failover.
- `agents/`: shared tool-calling loop (`base.py`), the five agents (`investigators.py`), prompts.
- `tools/`: read-only log, metrics and git tools; `evidence_check.py` (cited lines must exist); `sandbox.py`.
- `orchestrator/`: state machine (`pipeline.py`), contracts (`state.py`), approval gate, terminal view, report, replay.
- `db/`: schema and store. `ui/`: FastAPI app, background runner, static pages. `eval/`: scorecard.

## Sandbox
`SANDBOX_MODE=auto` uses Docker when it is running (`docker build -t incident-commander-sandbox sandbox/`), with no network
and CPU/memory limits. Without Docker it falls back to a subprocess in a temp copy with a scrubbed environment and a
timeout, which does not isolate the network.
