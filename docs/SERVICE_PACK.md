# Service packs

A service pack is one folder under `scenarios/` that tells Argus everything about a service it can investigate: its code
history, its telemetry, how to reproduce the failure, and what an outage costs. Argus's agents, tools, sandbox, approval
gate and reports are the same for every pack, so adding a service means adding data, not code.

```
python -m scenarios.pack new inventory_retries --service inventory-api   # a working starter pack
python -m scenarios.pack check                                           # validate every pack
python -m orchestrator.main scenarios/inventory_retries -v               # investigate it from a terminal
```

The starter pack runs as soon as it is made: it builds, its sandbox check reproduces the planted bug (retries switched
off), and the dashboard lists it. Replace its service, bug and telemetry with your own.

## Files

| File | Required | What it holds |
|---|---|---|
| `__init__.py` | yes | Empty; makes the folder importable |
| `history.py` | yes | `COMMITS`: list of `(iso_date, "Name <email>", message, {path: content})`, oldest first. `CULPRIT_INDEX`: the commit that causes the incident. Fixed dates and authors keep the shas the same on every machine |
| `generate_logs.py` | yes | `generate(out_dir, shas, culprit_index) -> dict`. Writes `logs/*.log`, `alert.json` and `expected.json`. Must be deterministic (seeded random) |
| `repro.py` | yes, unless `argus.yaml` names its own | `python repro.py <repo_dir>`: exit 0 when healthy, 1 when the failure reproduces. The sandbox runs it before and after a fix, with no network. A pack with an `argus.yaml` ([CONNECT.md](CONNECT.md)) sets its own repro command and files in any language instead |
| `business.json` | yes | What an outage costs; see below |
| `live.json` | no | `{"app", "url", "deploy_on_approve"}` for a service backed by a running app (like ShopFast): approved fixes are committed to its repo |
| `../service_maps/<service>.json` | no | Nodes and edges for the impact graph. Without one, the Impact graph tab says there is no map |

`repo/` and `logs/` are generated by `python -m scenarios.build <name>` (Argus also builds a pack on first use).

### Logs

One event per line, starting with an ISO timestamp (`2026-10-22T14:06:43.030Z` or `2026-10-22 14:06:45.000 UTC`), so the
log tools can search by time window. Put a misleading clue in the loudest signal (the "trap") and the real evidence in
quieter lines: a deploy record, a config value, a metric that stays flat. Argus has to refute the trap from evidence.

### alert.json (written by generate_logs.py)

`id`, `service`, `title`, `severity` (`sev1`–`sev4`), `started_at`, `fired_at`, and optionally `metric`, `value`,
`threshold`, `window`. A Prometheus Alertmanager webhook whose `service` label matches opens an incident for this pack.

### expected.json (written by generate_logs.py)

The answer key used by the evaluation and by the chatbot comparison on the ticket: `category` (`code`, `config`,
`resource` or `dependency`), `culprit_sha`, `file`, `trap` (the misleading clue in plain words) and `fix_hint`.

### business.json

| Key | Meaning |
|---|---|
| `service_label`, `unit` | What fails, in business words ("Checkout", "orders") |
| `units_per_minute`, `value_per_unit`, `currency` | Normal volume and value of one unit |
| `failure_share` | `"alert"` to use the alert's measured value, or a fixed share such as `0.08` |
| `manual_mttr_minutes`, `engineers_paged` | A typical manual fix for this kind of incident |
| `engineer_cost_per_hour` | Optional; prices the engineer time saved |
| `assumptions` | Plain sentences shown next to every figure |

## What every pack gets for free

Planner, investigator, fact checker (every quote checked against the real files), change finder, fixer, sandbox, the
approval rules in `policy.yaml`, the hash-chained audit log, business impact, the Value page, the report and the chatbot
comparison.
