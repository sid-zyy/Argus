Argus Connect

Point Argus at any application

Argus's agents are written once. To look after another application you don't change them: you describe the application in one file, argus.yaml. ShopFast (Python) and QuickBite (Node.js) below are two very different apps run by exactly the same agents.

What Argus needs from your application

Four things. Argus only reads them; it never changes your systems without a person's approval.

Its codeA git repo, so the agents can read the code and find the change that broke it.repo:
Its alertsYour monitoring tool sends a webhook to Argus when something crosses a threshold.alerts:
Its logsThe app's logs, its metrics, deploy records, and the logs of what it depends on, like its database.logs:
A health checkA command that fails while the problem is happening and passes once it's fixed. Fixes are tested with it.commands:

Connect a new application, step by step

About ten minutes. The example is a billing service with a Postgres database.

  1. Start the wizard

    It asks for the repo, the monitoring tool, each log file and the health-check command, detects JSON and CSV log formats, and writes scenarios/billing_api/argus.yaml. You can also copy an existing one and edit it.

    python -m connect.wizard new billing_api

  2. Say where the code is

    A local checkout, or a URL that Argus clones on first use.

    repo:
  path: C:/code/billing-api        # or  url: https://github.com/acme/billing-api.git

  3. Add the logs, including the database

    Give each log a name and say what it is. The role matters: the fact checker won't confirm "the database is the problem" from your app's errors alone; it needs the database's own log.

    logs:
  - {name: app.log,     adapter: jsonl, path: logs/app.jsonl,     role: service}   # your app
  - {name: metrics.log, adapter: csv,   path: logs/metrics.csv,   role: metrics}
  - {name: deploy.log,  adapter: jsonl, path: logs/deploys.jsonl, role: deploy}    # CI records
  - name: db.log                                                                 # the database
    adapter: command
    run: docker logs billing-postgres --since 2h
    role: dependency
    dependency: Billing database
    Connecting a database. Argus doesn't log in to your database or run queries on it. It reads the database's own log: slow queries, connection counts, locks, errors. Use adapter: text with a path if the log is a file, or adapter: command to read it from docker logs, kubectl logs or a cloud CLI. Name it as a dependency and the agents can prove or rule out the database.

  4. Write the health check

    A small script that replays the failing request against the repo: exit 0 when healthy, non-zero while broken. Argus runs it on a throwaway copy before and after a fix, then your tests. A fix only reaches a person if the check goes from failing to passing.

    commands:
  files: [checks/repro.py]
  repro: python checks/repro.py {repo}       # {repo} is the sandbox copy
  test: python -m pytest -q {repo}/tests

  5. Check it

    Every adapter is validated, and --full runs the health check and tests once in the sandbox. Argus refuses to start an incident for a service whose check has errors.

    python -m connect.wizard check billing_api --full

  6. Send its alerts to Argus

    Add Argus as a webhook in your monitoring tool. The alert's service label picks the application.
